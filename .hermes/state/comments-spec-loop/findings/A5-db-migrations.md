# Relatório: banco de dados e migrations — AtendON

## 1. Runner, idempotência, versionamento e rollback

- O entrypoint é `apps/backend/src/db/migrate.ts:1-25`, que resolve o diretório SQL e chama `runMigrations`; o runner lista automaticamente todos os `.sql` e ordena lexicograficamente (`apps/backend/src/db/migration-runner.ts:80-85`).
- Há lock global via advisory lock e ledger `schema_migrations` (`filename` PK, SHA-256, modo e timestamp): `apps/backend/src/db/migration-runner.ts:76-94,135-147`.
- Cada migration roda em transação própria; falha faz `ROLLBACK`, sucesso registra como `applied` (`apps/backend/src/db/migration-runner.ts:183-200`). Existe adoção segura de baseline para banco preexistente, registrada como `adopted` (`apps/backend/src/db/migration-runner.ts:158-180`).
- Não existe mecanismo automático de rollback/down: o rollback transacional só desfaz a migration que falhou. Rollback manual aparece como comentário explícito em `apps/backend/src/db/migrations/0129_tenant_loss_reason_catalog.sql:29-34`; a migration pendente alerta que DROP é irreversível (`apps/backend/src/db/migrations-pending-approval/README.md:40-42`).
- Idempotência não é garantida pelo runner; é propriedade de cada SQL. O exemplo 0129 declara uso de `IF NOT EXISTS`, `ON CONFLICT` e constraints condicionais (`apps/backend/src/db/migrations/0129_tenant_loss_reason_catalog.sql:26-27`). 0130 usa no-op por tenant/configuração e marcador no prompt (`apps/backend/src/db/migrations/0130_newave_sales_script_prompt.sql:10-14,22-26,38-41`). 0131 condiciona DROP/ADD pela existência da constraint (`apps/backend/src/db/migrations/0131_cascade_meeting_confirmation_outbox.sql:3-21`).

## 2. Convenção e formato

- Arquivos são `NNNN_nome_em_snake_case.sql`, ordenados por nome; não há registro manual (`apps/backend/src/db/migration-runner.ts:80-85`; README:7-16). Há lacuna histórica: coexistem `0010_listening_window.sql` e `0010_usage_provider_request.sql`; portanto o prefixo deve ser único para novas migrations, apesar da ordenação textual.
- 0129 começa com comentários de contexto/compatibilidade/rollback e depois SQL declarativo, tabela, índices, seed, função/trigger e ALTERs (`apps/backend/src/db/migrations/0129_tenant_loss_reason_catalog.sql:1-34,36-53,55-104,106-157`). 0130 é um bloco `DO ...` de atualização de prompt (`apps/backend/src/db/migrations/0130_newave_sales_script_prompt.sql:1-14,95-119`). 0131 é `DO $$` condicional de FK cascade (`apps/backend/src/db/migrations/0131_cascade_meeting_confirmation_outbox.sql:1-23`).

## 3. Teste fresh-migrations

- Sim. O nome da última migration é fixado em **2 lugares** no mesmo arquivo: `apps/backend/tests/fresh-migrations.integration.test.ts:32` (assert de `result.applied.at(-1)`) e `:287` (fixture/expectation `latestMigration`). Ao adicionar migration nova, atualizar esses dois literais nesse arquivo; não foi encontrado outro teste que fixe `0131`/`fresh-migrations`.

## 5. Tipos e timestamps

- IDs são predominantemente `UUID` com `gen_random_uuid()`, não `serial`; por exemplo `lead_loss_reasons.id UUID ... DEFAULT gen_random_uuid()` (`apps/backend/src/db/migrations/0129_tenant_loss_reason_catalog.sql:36-38`). FKs e IDs dos exemplos recentes também são UUID (`.../0130...:2-8`). Existem tipos integer para contadores/ordenação, mas não há convenção global de serial observada.
- `created_at`/`updated_at` não são universais: tabelas de domínio frequentemente usam ambos com `TIMESTAMPTZ NOT NULL DEFAULT now()` (0129:45-46), enquanto tabelas legadas têm combinações diferentes.
- Há trigger de atualização automática apenas para o conjunto Tripz AI: função e cinco triggers em `apps/backend/src/db/migrations/0114_tripz_ai.sql:276-298`. Em geral o código atualiza `updated_at` explicitamente; não assumir trigger padrão.

## 6. Banco de testes

- Backend scripts: `migrate` chama `tsx src/db/migrate.ts`, `migrate:test` chama `tsx scripts/migrate-test.ts`, e `test` chama `tsx scripts/run-tests.ts` (`apps/backend/package.json:7-31`).
- `migrate:test` carrega ambiente, resolve URL de teste, conecta PostgreSQL e executa o mesmo runner contra `src/db/migrations` (`apps/backend/scripts/migrate-test.ts:1-14`), depois instala trigger test-only para capabilities legadas (`:15-37`).
- `npm test` é wrapper: carrega ambiente, resolve DB/Redis de teste e força `NODE_ENV=test`, `DATABASE_URL` e `REDIS_URL` antes de iniciar Vitest (`apps/backend/scripts/run-tests.ts:1-18`).

## 8. Changelog/versionamento

- `changelog.json:2` indica versão atual `1.22.0`; histórico guarda versão, data, mudanças e commit (`changelog.json:2-15`).
- `scripts/changelog-bump.mjs` lê `package.json`/`changelog.json`, calcula diff desde o último commit do histórico, exclui changelog/package files, escolhe `patch/minor/major` por tamanho (ou `VERSION_BUMP`) e grava nova versão/entrada (`scripts/changelog-bump.mjs:1-18,42-74,180-223`). Sem diff, não altera (`:194-196`).
- Adicionar migration **não exige bump SemVer intrínseco no runner**. Porém, no fluxo de release/build, a migration entra no diff e pode disparar o `changelog-bump`; a versão é alterada no `package.json` raiz e changelog gerado (`scripts/changelog-bump.mjs:206-223`).
